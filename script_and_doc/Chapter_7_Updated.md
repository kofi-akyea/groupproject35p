# Chapter Seven: Conclusions and Critical Self Evaluation

## 7.1 Introduction

This chapter concludes the dissertation by synthesising the study's outcomes against its four objectives, articulating the theoretical and practical contributions, acknowledging the limitations that circumscribe the findings, and offering recommendations for future research. The final section comprises individual critical self evaluations written in the first person, in which each team member reflects honestly on their strengths, weaknesses, and the principal challenges encountered during the project.

## 7.2 Synthesis of Findings Against Objectives

The overarching aim of this study was to design, implement, and evaluate a web-based intelligent Decision Support System (DSS) that integrates supervised machine learning, explainable artificial intelligence, and interactive analytics for project risk prediction, while generating reusable design knowledge. The four operational objectives were addressed as follows.

**Objective 1 – Data Engineering:** The project risk dataset was successfully validated and prepared. Exploratory analysis confirmed 4,000 complete records and identified the four-level ordinal risk structure. The reproducible preprocessing pipeline handled missing values, applied context-appropriate encoding strategies, and selected 18 theoretically meaningful features defined in the configuration file. Special handling was implemented for `Stakeholder_Engagement_Level` conversion from categorical to numeric. Stratified data partitioning preserved the class distribution across training (2,800), validation (600), and test (600) sets. The output was a clean, fully documented analytical dataset ready for machine learning.

**Objective 2 – Model Development and Explainability:** Random Forest and Multinomial Logistic Regression were implemented and compared. The Random Forest achieved a test set accuracy of 50.7%, a macro-averaged F1 score of 0.508, and a quadratic weighted Cohen's Kappa of 0.622. Logistic Regression achieved slightly higher QWK (0.666) with similar accuracy (50.2%). The within-one accuracy of 92.7% for Random Forest indicates that severe misclassifications are rare. SHAP-based global and local explanations were integrated, providing both overall feature importance rankings and per-prediction natural language narratives. The explanation engine includes robust error handling for empty SHAP values to ensure reliability during batch predictions.

**Objective 3 – DSS Artefact Development:** A three-tier architecture was implemented, comprising a Flask REST API, a Streamlit dashboard, and a serialised data/model layer. The API exposed `/predict`, `/explain`, and `/health` endpoints with input validation and error handling. The dashboard delivered an interactive interface with five pages: Home, Predictor, Analytics, Model Performance, and Data Upload. A new Data Upload feature was added to support batch processing of CSV and Excel files using an optimised `predict_batch()` function that skips SHAP computation for performance. Integration and functional tests confirmed that all tiers communicated correctly and that the system met its response time target of under two seconds.

**Objective 4 – Artefact Evaluation:** The integrated DSS was evaluated through structured system testing, including unit tests, integration tests, end-to-end scenarios, performance benchmarking, and explanation quality inspection. Five defects were identified and resolved during testing: SHAP index out of bounds error, slider type mismatch, bar chart color length error, categorical string to float error, and bold text asterisks. The evaluation confirmed that the artefact was functionally correct, performed within specified limits, and produced clear, faithful explanations.

Taken together, these outcomes demonstrate that a Design Science Research approach can produce a functioning, integrated, and transparent DSS for project risk prediction, directly answering the primary research question.

## 7.3 Theoretical and Practical Implications

This study contributes to theory and practice in three main ways. First, it extends the literature on project risk analytics by demonstrating that an ordinal, four-level classification scheme—incorporating a distinct Critical category—can be successfully modelled and evaluated with ordinal-aware metrics such as quadratic weighted Kappa and within-one accuracy. This addresses the gap identified in Chapter Two, where most studies simplify risk into binary or three-class problems.

Second, the study contributes design knowledge for integrating XAI into interactive DSSs. The combination of global SHAP plots for model-level understanding and local natural language narratives for instance-level explanation provides a template for balancing model complexity with user-facing transparency. The decoupled three-tier architecture, where the explanation engine resides in the API and the frontend renders human-readable output, is a reusable architectural pattern applicable beyond project management.

Third, the evaluation framework—encompassing functional testing, performance measurement, and explanation quality inspection—offers a comprehensive, replicable method for assessing intelligent DSS artefacts. This moves beyond the purely metric-based evaluations that dominate the machine learning literature and aligns with the DSR principle that artefacts should be assessed for utility, not just accuracy.

Practically, the study delivers a working prototype that demonstrates how organisations might leverage open-source technologies (Flask, Streamlit, scikit-learn, SHAP) to build in-house risk prediction tools. The dashboard's what-if functionality illustrates how interactive analytics can support risk mitigation planning, enabling project managers to identify which factors, if addressed, would most effectively lower the risk profile of a project. The Data Upload feature extends this capability to batch processing, supporting analysis of multiple projects simultaneously.

## 7.4 Limitations

The study acknowledges several limitations. The exclusive use of a synthetic dataset, while necessary for reproducibility and methodological transparency, means that the predictive performance figures may not generalise to real organisational data. The moderate accuracy (50.7%) reflects the complexity and potential noise in the synthetic dataset. No multi-user stress tests were performed, and the system was evaluated only in a local, single-user environment. Consequently, scalability and robustness under concurrent load remain untested. The usability of the dashboard was assessed informally by the development team rather than through a structured study with practising project managers, limiting the strength of conclusions about its practical acceptability. Finally, the security of the web application was not subjected to penetration testing, which is essential for any production deployment but lay outside the scope of this proof-of-concept project.

These limitations are consistent with the study's scope, which prioritised the design and technical evaluation of an integrated artefact. They do not invalidate the findings but define the boundaries within which the contributions should be interpreted.

## 7.5 Recommendations for Future Research

Future work should address the limitations identified above. First, the DSS should be evaluated using one or more real-world project datasets, subject to appropriate data sharing agreements, to assess the generalisability of the predictive models and explanations. Second, a formal usability study with professional project managers, employing instruments such as the System Usability Scale supplemented by explanation-specific questions, would provide robust evidence of the dashboard's effectiveness in practice. Third, the system should be deployed in a containerised, cloud-based environment and subjected to load testing to evaluate scalability and to identify bottlenecks in the API or explanation pipeline. Fourth, the machine learning component could be extended with additional algorithms (e.g., gradient boosting, ordinal regression models) and evaluated using a broader set of ordinal metrics. Fifth, the explanation interface could be enriched with contrastive and counterfactual explanations to help users understand not only why a particular risk level was predicted, but what changes would shift the prediction to a lower risk category. Finally, integrating the DSS with existing project management information systems via standard APIs would move the artefact from a standalone prototype towards an embeddable decision support service.

## 7.6 Critical Self Evaluation

This section contains individual reflections from each team member, written in the first person. These evaluations honestly appraise personal strengths, weaknesses, and the key challenges faced during the project.

### 7.6.1 Samuel Kwesi Bonku – Data Engineering

When I began the data engineering role, I was confident in my Python skills but had limited experience with the systematic preprocessing of high-dimensional categorical data for machine learning. My main strength was persistence: I invested considerable time in exploratory data analysis, producing visualisations and frequency tables that gave the entire team a solid understanding of the dataset's structure. The discovery of the validation errors in the raw data (NaN values in governance columns and out-of-range communication frequency) occurred during this phase, and I was able to implement appropriate imputation and clipping strategies.

My principal weakness was an initial tendency to rely on default preprocessing choices without fully considering their downstream effects on explainability. For example, I originally did not properly handle the `Stakeholder_Engagement_Level` conversion, which caused type conversion errors during inference. Feedback from the team prompted me to implement a more nuanced strategy with explicit mapping from categorical to numeric values. This episode taught me that data preparation is not solely a technical process but a design activity with implications for model interpretability and user experience.

The biggest challenge I faced was ensuring reproducibility. Early in the project, I made changes to the cleaning script and forgot to update the serialised pipeline; this caused a feature mismatch when the API was tested. After that, I implemented strict version control for all artefacts and added the configuration file (config.py) as the single source of truth for feature specifications. I learned that in a multi-role project, a small oversight in data engineering can cascade into problems for everyone downstream.

Overall, I am proud of the robust, documented preprocessing pipeline I delivered. If I were to repeat the project, I would invest more time in feature selection experiments to provide stronger evidence for the final predictor set. I would also document the rationale for each preprocessing decision in a formal data preparation report from the outset.

### 7.6.2 Sylvester Ackah – Model Development and Explainability

My role involved the core predictive modelling and the integration of SHAP for explainability. My greatest strength was a methodical approach to model comparison and evaluation. I set up the evaluation framework early, using multiple metrics including accuracy, macro F1, quadratic weighted Kappa, and within-one accuracy to avoid the trap of optimising for overall accuracy while ignoring the ordinal nature of the problem. The decision to use quadratic weighted Kappa as an additional evaluation metric was one I am particularly pleased with, because it captures the ordinal nature of the problem in a way that conventional metrics cannot.

However, I underestimated the complexity of integrating SHAP explanations into a web application. In the initial implementation, the SHAP engine did not handle empty arrays, which caused index out of bounds errors during batch predictions. This taught me the importance of robust error handling in production ML systems. Once proper array length checks were added, the issue was resolved permanently.

A significant challenge was balancing model performance with explanation fidelity. The Random Forest and Logistic Regression showed similar performance, with neither clearly superior across all metrics. I spent considerable time validating that the SHAP values for both models were genuinely informative and not artefacts of the algorithms. Using TreeSHAP for the Random Forest gave me confidence in the output. I also learned to translate SHAP values into plain language sentences, which required thinking from a user's perspective rather than a data scientist's.

Looking back, I would have liked to implement an ordinal regression model (e.g., a cumulative link model) as a third baseline, to better handle the ordered class structure. That remains a clear avenue for future work. I also recognise that my evaluation focused on aggregate metrics; per-project error analysis, which would have identified patterns in the misclassifications, was not as deep as it could have been. Overall, I developed strong skills in model evaluation and explainability, and I now appreciate that building a trustworthy ML system requires as much effort on explaining outputs as on achieving high accuracy.

### 7.6.3 Kofi Awuette Akyea – DSS Artefact Development

My responsibility was to design and implement the web-based DSS architecture. Coming into the project, I had experience with Flask and Streamlit separately, but I had never integrated them into a cohesive three-tier system with a machine learning backend. My strength was a clear architectural vision from the start: I insisted on the three-tier separation, even when it would have been faster to build a monolithic Streamlit app with embedded model calls. This decision proved crucial when we needed to test the API independently and when the model needed to be retrained without touching the frontend.

My main weakness was in the area of input validation and error handling. In the first prototype, the API would return cryptic 500 errors if the input JSON was malformed, which was frustrating for the team during integration. After studying the Flask error handling documentation and working with Festus's test cases, I implemented a proper schema validation layer and meaningful error messages. This experience reinforced the software engineering principle that robustness must be designed in from the beginning, not patched on later.

The biggest technical challenge was managing feature name consistency across the pipeline. The preprocessing step renamed columns after one-hot encoding, while the dashboard used human-readable feature labels. I created a configuration file (config.py) that served as the single source of truth and wrote a mapping function that translated between the three naming conventions. This took longer than expected but eliminated an entire class of bugs.

I am satisfied with the dashboard's functionality, particularly the what-if scenario capability that allows users to adjust parameters and see updated predictions instantly. The Data Upload feature was a significant addition that required implementing a separate batch prediction function for performance. If I had more time, I would improve the visual design—the Streamlit default theme is functional but plain—and add more sophisticated interactive elements like a feature contribution radar chart. I also recognise that I did not implement any user authentication or session management, which would be essential for a production system. Overall, I developed a much deeper understanding of how to architect ML-powered web applications and the importance of clean interfaces between system components.

### 7.6.4 Festus Bouja – Artefact Evaluation

My role was to evaluate the developed DSS artefact through structured system testing. My background in software quality assurance gave me a foundation in test planning, but applying these skills to a machine-learning-enabled system was a new challenge. My main strength was the comprehensiveness of the test strategy: I insisted on covering not only functional correctness but also performance and explanation quality, and I designed the test cases to be traceable back to the project's requirements. The testing process identified five defects that were systematically resolved.

A weakness I identified in myself was a tendency to focus on positive test cases—verifying that the system worked under normal conditions—and to neglect edge cases. For instance, I did not initially test what happened when batch predictions encountered empty SHAP value arrays. This oversight was exposed during testing, and it led to a defect that required adding array length checks in the SHAP engine. From that point, I added negative and boundary test cases systematically, which significantly improved the system's robustness.

The evaluation of explanation quality was the most challenging aspect of my role. There are no widely accepted automated metrics for explanation quality, so I had to rely on a manual inspection using criteria from the literature (fidelity, comprehensibility, consistency). This felt subjective at times, and I would have preferred to involve external users to validate my assessments. This remains the most significant gap in the evaluation, and I fully acknowledge it.

I am proud of the defect tracking process I established. Every issue, no matter how minor, was logged and tracked to closure. This disciplined approach prevented problems from being forgotten and ensured that the final artefact was as polished as our timeline allowed. If I were to repeat this project, I would integrate the test suite into a continuous integration pipeline so that tests ran automatically on every code change. I would also develop a structured usability evaluation protocol, even for surrogate users, to provide more rigorous evidence for the dashboard's interface quality.

## 7.7 Chapter Summary

This chapter concluded the dissertation by confirming that all four objectives were achieved, resulting in a working explainable DSS for project risk prediction. Theoretical contributions include the operationalisation of ordinal risk classification with appropriate metrics (quadratic weighted Kappa, within-one accuracy) and the integration of XAI within a DSR framework. Practical implications point toward the feasibility of building transparent, interactive analytics tools for project managers, including a new Data Upload feature for batch processing. The acknowledged limitations—synthetic data, moderate predictive accuracy, absence of user testing, and minimal security evaluation—provide clear directions for future research, including real-world validation, usability studies, and architectural hardening. The critical self-evaluations offer honest, first-person insights into the learning and challenges experienced by each team member, completing the reflective dimension of the DSR process.
